# Database: one schema, any SQL backend

The schema is defined **once** in TypeScript using Kysely's schema builder ([packages/db/src/migrations](../packages/db/src/migrations)). It is compiled into dialect-specific SQL:

```
packages/db/migrations/
  sqlite/    ← Cloudflare D1 (and local SQLite under wrangler dev)
  postgres/  ← Postgres, PlanetScale Postgres, Neon, Supabase … (via Hyperdrive)
  mysql/     ← MySQL 8, PlanetScale (Vitess), MariaDB 10.6+ (via Hyperdrive or HTTP)
```

The generated `.sql` files are committed so you can review them. CI fails if they drift from the TypeScript source (`npm run check -w packages/db`).

## Choosing a backend

The driver is chosen **at build time** in `apps/worker/wrangler.jsonc`:

```jsonc
"define": { "__HELPDESK_DB_DRIVER__": "\"postgres\"" },   // d1 (default) | postgres | mysql | planetscale | all
```

esbuild drops every other driver from the bundle (see [Bundle size](#bundle-size)). `"all"` bundles every driver and lets the runtime `DB_DRIVER` var pick one. With a single-driver build, a mismatching `DB_DRIVER` fails with a clear error. `define` can be set per wrangler environment, so staging and production can use different backends.

| Driver | Connection | Migrations |
|---|---|---|
| `d1` (default) | D1 binding `DB` | `npx wrangler d1 migrations apply DB --remote` |
| `postgres` | Hyperdrive binding `HYPERDRIVE` (or `DATABASE_URL`) using `pg` | `npm run db:migrate -- --driver postgres --url …` |
| `mysql` | Hyperdrive binding `HYPERDRIVE` (MySQL origin; TLS required) using `mysql2` | `npm run db:migrate -- --driver mysql --url …` |
| `planetscale` | `DATABASE_URL` secret using the PlanetScale HTTP driver (no Hyperdrive needed) | `npm run db:migrate -- --driver mysql --url …` |

For **PlanetScale Postgres**, use `postgres` with Hyperdrive. For **a MySQL/Postgres server on your LAN**, put Hyperdrive in front of a Cloudflare Tunnel or Workers VPC. In local dev, `localConnectionString` on the Hyperdrive binding connects directly.

Only the selected driver is bundled. The others are removed at build time.

### PlanetScale (MySQL/Vitess) migrations

- **TLS is required.** Append `?ssl={"rejectUnauthorized":true}` to the `mysql://` URL you pass to `db:migrate`.
- **Branches with safe migrations reject DDL**, which is the recommended setup for production. The flow is:
  1. Run `npm run db:migrate -- --driver mysql --url <dev-branch-url>` against a **development branch**.
  2. Open a deploy request into production.
  3. Once it is deployed, run `npm run db:migrate -- --driver mysql --url <prod-url> --record-only`. This only records the migrations in `_helpdesk_migrations`.
- At runtime the Worker uses the HTTP driver (`DB_DRIVER=planetscale`). Its transactions run on a single server session.

### MySQL collation

All MySQL string columns use `utf8mb4_bin`, giving byte-exact comparison like SQLite and Postgres. With MySQL's default `utf8mb4_0900_ai_ci`, `jose@x` and `josé@x` would collide on the unique email index, and Message-ID matching would ignore case. The app lower-cases email addresses itself.

## Portability rules (why the schema looks the way it does)

| Concern | Rule |
|---|---|
| IDs | ULIDs generated by the app, stored as `varchar(26)` / `text`. No autoincrement, so `RETURNING` vs `LAST_INSERT_ID` never matters. |
| Timestamps | Epoch milliseconds in `bigint`, set by the app. No DB defaults, triggers or timezone types. |
| JSON | Stored as text (`mediumtext` on MySQL) and parsed in the app. Never queried inside SQL. |
| Booleans | `integer` / `smallint` / `tinyint` holding 0 or 1. |
| Indexed strings | `varchar(n)` on MySQL, because InnoDB can't index `TEXT` without a prefix. All indexes fit the 3072-byte utf8mb4 limit. |
| Foreign keys | Declared on SQLite and Postgres. **Omitted on MySQL** so the same SQL runs on PlanetScale/Vitess, where FKs are opt-in. The app enforces integrity there. |
| BIGINT in results | `pg` and PlanetScale return int8 as a string, so the drivers are configured to return numbers. |

## Atomic writes and ticket numbers

Ticket refs (`ACME-000123`) are sequential per mailbox, using a `counters` row.

- **Postgres / MySQL / PlanetScale** (`SqlRepo`): one transaction does `insert counter (ignore duplicate)`, `UPDATE counters SET value = value + 1`, `SELECT value`, then inserts the ticket, message, attachments and event. The `UPDATE` locks the counter row until commit, so concurrent creators serialise. A failed insert rolls back the number as well.
- **D1** (`D1Repo`): D1 has no interactive transactions, so the same writes go in one atomic `batch()`. The ticket insert reads the counter through a subquery.

A shared contract suite ([packages/db/test/repo-contract.ts](../packages/db/test/repo-contract.ts)) runs against every backend, covering:
- 8 concurrent ticket creations
- rollback on duplicate
- threading lookups
- pagination

| Backend | Where it runs |
|---|---|
| D1 | in workerd (`apps/worker/test/d1-contract.test.ts`) |
| Postgres | PGlite locally, plus a real `postgres:17` in CI |
| MySQL | a real `mysql:8.4` in CI (`.github/workflows/db.yml`) |

## Existing D1 deployments

The SQLite SQL used to be hand-written in `apps/worker/migrations/0001_init.sql`. It is now generated into `packages/db/migrations/sqlite/0001_init.sql`.
- Wrangler tracks applied migrations by **file name** in `d1_migrations`, so `0001_init.sql` is skipped on databases that already ran it.
- The generated DDL is behaviourally identical: `bigint` has INTEGER affinity, and the columns and index names are the same.
- Only `0002_provider_msgid_index.sql` is new.

## Bundle size

`connect.ts` puts each driver behind a branch that compares `__HELPDESK_DB_DRIVER__` directly. Wrangler's esbuild replaces that identifier with the configured literal, folds the comparison, and removes the dead branch together with its dynamic `import()`. Measured with `wrangler deploy --dry-run` (wrangler 4.151):

| `__HELPDESK_DB_DRIVER__` | Upload | gzip |
|---|---|---|
| `"d1"` (default) | 682 KiB | 129 KiB |
| `"planetscale"` | 888 KiB | 153 KiB |
| `"postgres"` | 1,030 KiB | 186 KiB |
| `"mysql"` | 2,223 KiB | 554 KiB (mysql2 + iconv-lite) |
| `"all"` | 2,483 KiB | 603 KiB |

Before this change, every build was the `"all"` size. Outside a wrangler build, for example in Node scripts or tests, the identifier is undefined, so a `typeof` guard includes every driver.

## Adding a migration

1. Add `packages/db/src/migrations/000N_name.ts` exporting `up(db, dialect)` that returns schema-builder statements. Use `columnTypes(dialect)` for portable types.
2. Append it to `src/migrations/index.ts`.
3. Run `npm run db:generate` and commit the generated SQL for all three dialects.
4. Apply it: run `wrangler d1 migrations apply` for D1, or `npm run db:migrate` for Postgres/MySQL. The runner records progress in `_helpdesk_migrations`.

Never edit a released migration. Add a new one instead.
